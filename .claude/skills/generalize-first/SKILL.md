# 先抽象，再修补

这个项目的开发节奏是"出了问题→写回归测试→修"。这个节奏本身是对的，2300 多项
回归和"每个数都能溯源"是项目最硬的资产。缺的是**修完之后回头抽象**这一步：
每次修复局部都对，积累下来却变成一圈只覆盖窄子集、照案例调参的特例。

这个 skill 不要求重构，只要求在写补丁前回答四个问题，并按结论选择做法。

## 四个问题

### 1. 我是不是在加一个类型标志或字符串分支？

信号：新增 `is_xxx` / `circular` 这类布尔字段，或在第 N 处写 `if kind == "..."`。

仓库里的现状：`Section` 只存 A/Iy/Iz/J/cy/cz 和一个 `circular` 标志，不知道
自己的形状，于是正应力要按标志分两套公式、剪应力缺几何只能不算、节点实体只能
支持圆管。`src/` 中按 `kind ==` / `analysis ==` 分支的地方已有约 50 处。

该做的：如果这个分支是"同一概念的不同实现"，它应该是**领域对象上的方法**，
由对象自己回答（形状自己给出应力校核点、一次矩、轮廓），而不是由调用方判断类型。

### 2. 这个常数是不是只在一个案例上标定的？

信号：常数旁的注释写着"实测某某节点""按某次运行"。

仓库里的现状：节点实体默认网格放粗规律（指数 1.8、余量 12%）只在一个 6 杆
D219×8 圆管节点上拟合（`src/native_joint.py` 的 `_ELEMENT_SIZE_EXPONENT`）。

该做的，按优先级：
1. 换成不需要标定的机制（例如按求解规模选择迭代求解器，而不是按经验放粗网格）。
2. 做不到时，把常数提成具名模块常量，注释写明**标定来源、适用范围**，并在超出
   范围时告警或拒绝，而不是默默外推。
3. 阈值必须与单位制无关，见 `frame-kernel` skill 第 2 节。

### 3. 我是不是在从已有数字反推本该存在的信息？

信号：用 A、I 反推截面形状，用坐标反推连接关系，用名字字符串反推类型。

仓库里的现状：`src/solid_joint.py` 的 `infer_circular_dimensions` 由 A/I 反推
圆管外径和壁厚；工字形反推不出来，于是节点实体"只支持圆管"。

该做的：在数据源头（Domain IR、builder、领域对象）**保存**这条信息，向下游传递；
旧数据缺这条信息时走迁移或明确拒绝，不要让下游各自猜。

### 4. 我是不是在为一道评测题或一个测试专门加规则？

信号：修复动机是"P02 那一轮没过""这个用例红了"，补的规则只描述那个现象。

该做的：先问这道题暴露的**一般性缺口**是什么，按缺口的语义来写规则。正面例子：
`src/agent.py` 的批量修改闸门没有按工具名判，而是在副本上试跑、按**实际效果**
累计计数，所以拆成多次单项修改也绕不过去。它仍有可改进处（按实体个数而不是按
修改是否触及支座/截面/拓扑来判），但思路是对的——照这个方向写。

## 三次规则：什么时候抽象

- **第一次**：就地修，正常写回归测试。在提交信息或 `docs/PROGRESS.md` 里写一句
  "这是 X 类特例"。
- **第二次**：仍可就地修，但在 PROGRESS 里把两处并列记下，说明它们是同一个缺口。
- **第三次**：停下来提抽象，不再加第三个特例。抽象作为单独的提交或 PR。

搜同类补丁：`grep` 相同的标志名、相同的字符串常量、相似的"实测"注释；读相关
模块的文件头文档字符串，那里常记录着之前的特例。

## 怎么安全地抽象

1. **先锁行为**：现有测试全绿；不够的先补"旧行为不变"的回归测试。
2. **扩展领域对象，保留旧接口**：例如新增 `Shape` 协议并让旧 builder 返回的 dict
   仍可用；旧的 Domain IR 通过 `migrate_payload` 迁移，不让旧模型数值变化。
3. **一次只引入一个抽象**，每个抽象替换掉至少两处已有特例，证明它确实是共性。
4. 抽象完成后，删掉被替代的标志、分支和反推函数，不留两套并行路径。
5. 数值结果逐字节或在原容差内与旧实现一致；能力扩大的部分另加闭合解测试。

## 什么时候不要抽象

- 数值内核用"函数 + numpy 数组"是正常写法，不必为了面向对象而套类。
- 有意为之的领域模板（`generator.py`、`bent.py` 的规则框架、一榀拉伸）本来就是
  专用的，不要把它们泛化成通用建模器。
- 只有一种实现时不建插件框架、注册表或工厂；等出现第二、第三种再说。
  （与全局 `karpathy-guidelines` 的"不过度设计"互补：那边防过度设计，这边防过度特例化。）
- 临近答辩或冻结版本时只就地修，把抽象需求写进 PROGRESS 的"下一步"。

## 在回复与提交中说明

改完后，在给用户的回复（以及必要时的提交信息）里用一句话说明：

- 这次改动是**通用机制**还是**特例补丁**；
- 若是特例，它属于哪一类、目前是第几处；
- 若引入了标定常数，标定来源与适用范围是什么。
