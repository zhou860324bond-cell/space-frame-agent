三、发现的优点

  • 数值正确性极高。 解析解机器精度命中；Abaqus B33 五算例全场误差 1e-6~1e-5，工程上可视为精确。弱轴弯曲（857mm）与强轴（42.9mm）分开验证，截面主轴方向无错误。
  • 架构原则清晰且被遵守。 "大模型只产结构、不产数值"通过离线演示得到验证——每个数字都来自工具返回值，调用链在面板中摊开展示，自证可溯源。
  • 自修复闭环真实可用。 agent_demo 完整展示"求解失败→奇异诊断→补约束→重算→平衡校核通过"的 8 轮闭环，是工程上最亮眼的能力。
  • 功能覆盖面广且有深度。 多工况/组合、静力凝聚释放、屈曲、模态、截面参数扫描、命名集合、支撑/抽柱/换截面算子、Word 报告生成，demo_portal 一次跑通全链路。
  • 测试设计有方法论。 评分器读会话状态而非回复文本；Abaqus 对标选 B33（苹果对苹果）并主动展示 B31 格式差异；健壮性测试写不变量而非"多跑几次"；对 UTF-8 控制台、Qt 绑定、奇异不报错等坑有系统性处理。
  • 文档质量高。 README 与各模块 docstring 把"为什么这么做"讲透（如局部坐标系参考向量、内力回算、空集合静默等），工程可读性很强。
  • 双界面策略务实。 网页版功能等价且在本机正常可用；桌面端代码结构完整、自检项全面，OpenGL 问题属环境性。

四、发现的问题与改进建议

问题 1（严重）· 完整测试套件在 PyVista 渲染处崩溃

全量 pytest 在约 27% 处、桌面端渲染相关测试在 viewport.show_deformed → add_mesh → reset_camera → render 路径上抛 Windows access violation，进程直接被带崩，多次复现（单独跑一个测试文件也崩）。本机无有效 OpenGL（见问题 2），但 conftest.py 只处理了"窗口未关闭导致析构崩溃"，没有拦截渲染期崩溃，也没有做无 GL 环境隔离。

建议：桌面端渲染测试统一加 @pytest.mark.skipif(无可用GL) 或自检失败即 skip；把渲染调用包进 try/except 或子进程隔离，绝不允许一个测试把整个 pytest 进程带崩。README 声称"710 测试全绿"在本机当前状态下不成立。

问题 2（严重）· doctor 自检与实际启动不一致，桌面端打不开

--doctor 报告"OpenGL 离屏渲染正常"，但真实 python -m desktop.app 启动时 VTK 报 failed to get valid pixel format / Failed to initialize OpenGL functions! 并退出。即：自检没覆盖真实渲染路径（离屏上下文 ≠ Win32 窗口上下文），用户按 README 提示"自检通过就是能开"会被误导。

建议：把 doctor 的 OpenGL 检查升级为创建真实 RenderWindow 并渲染一个 mesh（正好复现崩溃路径），OpenGL 失败时明确报"桌面端不可用，请用网页版"，而不是报"正常"。这在 README 已有预案（无 GL 用网页版），只是检测没落到点。

问题 3（中等）· 3 个单元测试失败，其中 2 个与 Abaqus 环境假设有关

  • test_compare_solvers.py::test_comparison_says_which_side_failed — monkeypatch 把 abaqus_available 置 False，但 solve() 内部实际调用 find_abaqus()（patch 错函数）。本机装有 Abaqus，于是测试真的去跑了一次 Abaqus 作业并成功，assert not r.ok 落空。这是测试 bug，同时暴露 solve() 绕过 abaqus_available() 的口径不一致。
  • test_gui.py::test_comparison_tab_degrades_gracefully_without_abaqus — 假设无 Abaqus 时的降级提示，本机有 Abaqus 故提示不出现。测试应自动探测（find_abaqus() is None 才断言降级文案），而非写死假设。
  • test_drawing.py::test_drawing_a_two_bay_frame_takes_no_redundant_clicks — 期望 6 根杆，实际画出 5 根（左柱/左梁/中柱/右梁/右柱，无重合节点，结构完全正确）。是期望值写错了（应为 5），不是功能 bug。

建议：降级类测试统一改为"真实探测环境"再断言；补一个"patch find_abaqus"的用例覆盖 solve() 的失败路径；修正 test_drawing 期望值。

问题 4（中等）· 真实大模型评测 13/14，A01 简支梁集中力稳定失败

14 题评测通过 13（93%）。A01"单跨 8m 简支梁跨中 50kN 集中力"两次运行均得 max_displacement_mm = 0.0（期望 8.4656 mm）——大模型建出的模型位移为零。已排除求解器问题：手动同参数建模，求解器精确命中 8.465608465608467 mm。同类的 A02 悬臂梁、A03 简支梁均布荷载均通过，独 A01（集中力 + 未明确梁轴向）失败。

建议：① 在系统提示/工具说明中明确"简支梁请先说明轴向与荷载平面"；② 评估 A01 题目本身对模型的表述苛刻程度（未给梁方向），必要时补方向；③ 将 A01 列为回归样例；④ README"14 题六类全过"应更新为当前 13/14 或注明达标环境。

问题 5（轻微）· 若干工程细节

  • examples/run_json.py 等源码存在 SyntaxWarning: invalid escape sequence '\p'，建议统一为 raw string 清理。
  • 评测/示例运行会直接覆盖 evalset/report.md、benchmark_*.md 等报告文件（本次测试即覆盖了 report.md 的历史成绩单，已通过全量重跑恢复为 14 题成绩）。建议默认写时间戳副本或用 run_repeat.py 归档，防止误覆盖。
  • 崩溃后留下无法用普通权限终止的 python 残留进程（CPU 占用 0，重启后自然消失），与 VTK 崩溃相关，建议排查窗口/线程收尾。
  • README 顶部"710 个测试全绿"与历史 run_log.txt（早期仅 41 个测试、agent_demo 曾崩在 UTF-8）需要与新环境对齐，避免口径不一致。
