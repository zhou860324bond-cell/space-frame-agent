## 0. 一句话判断

**单个按钮基本都有了，差的是把它们串起来的操作语法；而语法上不去的根子在数据模型。**

我们的数据是「逐实体属性表」：每个节点一条支座记录，每根杆写着自己的截面名，
荷载逐条挂在节点或杆件编号上。这是 SAP2000 表格式的组织方式。Abaqus 的组织方式是
「有名字的特征对象施加在区域上」：一个边界条件对象施加在「柱脚」集合上，一个截面
指派对象指向「边柱」集合。在逐实体的数据上，界面只能模仿 Abaqus 的外观，做不出它的
逻辑——比如「边界条件 BC-柱脚」在数据里根本不存在，存在的是 20 条同名的节点记录，
模型树只能靠按名字分组把它们拼回来（`model_tree.py` 中 `kinds` 的分组）。

所以规划分两层：**先在界面层把操作语法做顺**（不改数据格式，冻结前可交付），
**再把数据模型升级为区域对象**（冻结后，涉及迁移与 Agent 工具）。

## 1. Abaqus 为什么顺手：七条操作原则

| 编号 | 原则 | 用户感受 |
|---|---|---|
| P1 | **对象化**：材料、截面、截面指派、集合、分析步、边界条件、荷载、幅值、作业、输出请求都是有名字的对象 | 能在一个地方看到、改、删、复制任何东西 |
| P2 | **区域化**：对象施加在区域（集合或现场拾取）上，不施加在编号上 | 改一次集合，所有引用它的对象自动跟着变 |
| P3 | **分析步是唯一主线**：静力、频率、屈曲都是分析步类型；荷载和边界条件在某一步创建并向后传播 | 只有一条时间轴，不用猜哪个设置在起作用 |
| P4 | **统一操作语法**：命令 → 提示区说明要选什么 → 拾取（多选、框选或用集合）→ 完成 → 编辑器；每类对象都是「创建 / 编辑 / 管理器（复制、重命名、删除、抑制）」 | 学会一类对象，就会所有对象 |
| P5 | **模型树即操作中心**：右键菜单、管理器、工具箱是同一组动作 | 不需要记功能区在哪 |
| P6 | **模型与作业、结果分离**：作业有提交、监控、消息；模型改了，旧结果仍可查看，只标记为过期 | 敢改模型，不怕丢结果 |
| P7 | **模块即上下文**：切到属性模块按截面着色，切到载荷模块显示当前步的荷载 | 视口始终显示与当前操作相关的东西 |

## 2. 现状逐条对照

| 原则 | 现状（证据） | 差距 |
|---|---|---|
| P1 对象化 | 材料、截面、工况、组合、分析步、幅值是对象；**边界条件、荷载、截面指派不是对象**，是逐节点/逐杆件的字段（`model_io.py` 中 `supports` 每项一个 `node`，`members` 每项自带 `section`/`material`） | 大 |
| P2 区域化 | 内核和 Agent 有 `define_set`，`set_supports` 等工具接受集合名，但写入时立即展开成编号，**集合不是活的引用**；界面与模型树**完全看不到集合** | 大 |
| P3 分析步主线 | 工况与组合、分析步（`step_dialog.py`）、求解设置（线性/P-Δ/材料）、模态按钮、屈曲按钮**五个入口并存**；边界条件面板按工况组织；**创建载荷对话框把工况下拉框标成「分析步」**（`load_dialog.py:202`） | 大，且已在界面上造成概念混乱 |
| P4 统一语法 | 先选命令再拾取**已部分实现**：`_require_selection` 会进入拾取并在点中后自动续上命令，提示区有说明。但**选择状态只有一个** `_selected_id`：不能多选、不能框选、没有「完成」、不能用集合代替拾取 | 中 |
| P4 统一管理 | 同类对象多入口：支座有「支座管理器」「创建边界条件」「边界条件管理器」三处，荷载有「载荷管理器」「创建载荷」两处，材料截面有「截面管理器」「创建材料」「创建截面」「属性指派」四处；行为各不相同 | 中 |
| P5 模型树 | 树只显示、只响应双击（`model_tree.py` 文件头明写「树只显示，不改模型」）；**没有集合、分析步、幅值、作业分支**；每次整棵重建 | 中 |
| P6 作业与结果 | F5 直接求解；没有作业对象和消息记录；任何建模修改都清除结果（撤销命令的提示「结果会一并清除」） | 中 |
| P7 模块上下文 | 功能区页签切换只换按钮，视口显示模式需单独切换；没有「当前分析步」选择 | 小到中 |
| 拾取精度 | 拾取先要点中 VTK 表面，再按「模型尺寸的 10%」找最近对象（`scene.nearest`），容差在世界坐标里；大模型或缩放后容易选到邻居或选不中 | 小，但直接影响手感 |

**我们比 Abaqus 强、要保留的**：每个界面操作都经过 `Session.dispatch` 记入建模历史，可以回看、跳回、导出轨迹（相当于 Abaqus 的 `.jnl` 回放，但带人话摘要）；Agent 与界面共用同一套工具；所有数值可溯源。规划中的每一项都不能破坏这三点。

## 3. 目标架构

### 3.1 概念模型（决定）

| 概念 | 定义 | 说明 |
|---|---|---|
| 集合 Set | 有名字的节点集、杆件集 | 现有数据结构保留；升级后成为被引用的区域 |
| 截面指派 SectionAssignment | 区域 + 截面（+材料） | 升级前由界面层批量写 `members[].section` |
| 边界条件 BC | 名字 + 区域 + 自由度/弹簧 + 创建于哪一步 | 升级前由界面层批量写 `supports` 和 `steps[].supports` |
| 荷载工况 Load Pattern | 现在的 `load_cases`，**界面统一改叫「工况」** | 结构设计离不开工况和组合，保留 |
| 荷载 Load | 名字 + 区域 + 类型与大小 + 所属工况 | 升级前逐条写入工况 |
| 分析步 Step | 类型（静力 / P-Δ / 频率 / 屈曲）+ 激活哪些工况（带幅值）+ 本步边界条件变化 | 沿用 `src/steps.py` 的传播语义；**新增频率、屈曲两种步类型**，取代独立的模态、屈曲按钮 |
| 荷载组合 Combination | 结果层的线性叠加 | 只对线性静力步有效，保留现有规范组合 |
| 作业 Job | 一次提交：模型快照哈希 + 分析步列表 + 状态 + 消息 + 结果库 | Result DB 已经记录模型哈希，作业是它的外壳 |

关键决定：**不照搬 Abaqus「荷载直接属于分析步」**，而是「荷载属于工况，分析步激活工况」。
这正是 `steps.py` 现有的 `loads: 工况名 → 幅值名` 语义，内核不用改；对只做线性静力的
用户，默认的 Step-1 激活全部工况，他可以完全不碰分析步。

材料非线性暂不进入分析步，理由见 `src/steps.py`：一步内多个工况同时生效，材料非线性
不能事后叠加。它继续留在「求解设置」中，作为单工况的专门分析，并在界面上写明这一点。

### 3.2 交互层

1. **统一拾取会话（PickSession）**——所有「需要区域」的命令都走它：
   - 提示区：「选择要施加边界条件的节点」+「完成」「取消」「使用集合…」；
   - 多选：Shift 加选、Ctrl 减选；拖动框选（屏幕空间矩形）；全选当前过滤类型；
   - 也可以在模型树里点集合作为区域；
   - 拾取容差改为**屏幕像素**，不再按模型尺寸比例；
   - 命令前已有选择时，直接作为默认区域（保留现在「先选后点」的用法）。
2. **通用对象管理器**：一个按对象类型参数化的管理器（列、创建、编辑、复制、重命名、删除、抑制）；
   与分析步相关的对象（边界条件、工况激活）显示「每一步：新建 / 传播 / 修改 / 失活」矩阵。
3. **模型树 v2**：分支为 材料 / 截面 / 截面指派 / 集合 / 分析步 / 幅值 / 工况与荷载 / 边界条件 / 组合 / 作业 / 结果（按作业）；
   右键菜单复用功能区的 QAction；单击高亮对应区域；按对象标识增量更新，保留选中与展开状态。
4. **入口合并**：
   - 支座三个入口 → 「创建边界条件」+「边界条件管理器」；
   - 荷载两个入口 → 「创建载荷」+「载荷管理器」；
   - 材料截面四个入口 → 「材料管理器」「截面管理器」「截面指派」；
   - 求解设置、分析步、模态、屈曲 → 「分析步管理器」+「作业管理器」（材料非线性见 3.1）。
5. **模块上下文**：切到属性页按截面着色并显示未指派杆件；切到载荷页出现「当前分析步」下拉框，视口只画该步生效的荷载与边界条件；切到结果页显示当前作业。

### 3.3 Agent 层

- 新增或改造工具与界面操作一一对应：`create_bc(region, step)`、`create_load(region, case)`、
  `assign_section(region)`、`create_step(type)`、`submit_job`；`region` 接受编号列表或集合名。
- 旧工具（`set_supports` 等）保留为薄封装，37 题评测集必须保持通过；为集合、分析步、作业补评测题。
- 变更预演（`preview_change`）的实体级 diff 增加对象级描述：「BC-柱脚 区域由 18 个节点变为 20 个」。

### 3.4 结果层

- 结果按作业存放；模型修改后，作业标记「模型已修改，结果对应旧版本」，仍可查看，
  但显示的是作业自己的模型快照（建模历史中已有快照），不与当前模型混画。
  这与已有的「求解版本绑定」原则一致：不清除，而是绑定并标明。
- 后续再做：输出量选择器、路径曲线（沿一串杆件画内力）、显示组（隐藏或孤立部分杆件）、动画。

## 4. 验收方式：标准操作剧本

「流畅」要可度量。定一个标准剧本，在改造前后各走一遍，记录**点击次数、弹窗个数、
需要输入编号的次数、刷新耗时**：

> 两跨三层、进深两榀的空间钢框架：生成几何 → 定义 Q355 与两种 H 型截面 →
> 建集合「柱」「梁」「柱脚」→ 截面指派到集合 → 柱脚固接 → 工况「恒载」「活载」→
> 梁上均布荷载 → Step-1 静力、Step-2 频率 → 提交作业 → 查看弯矩云图与前三阶振型 →
> 把柱脚改成铰接，重新提交，对比两次作业。

- 改造前先测基线，写进本文；
- 剧本做成桌面端自动化测试（无头环境下逐步驱动 QAction 与拾取会话），防止以后回退；
- 同时补上 PROGRESS 中一直未做的「系统性刷新与交互耗时测量」。

## 6. 不做什么

- **不做 Assembly / Instance**：刚架只有一个「部件」，装配层只会增加步骤；
- **不做 Mesh 模块**：剖分由 `model_compiler` 自动完成，保留只读的「分析网格」查看；
- **不另建 Interaction 模块**：杆端释放、半刚性连接、刚域偏移以后作为「连接」对象进入模型树即可；
- **不为了像 Abaqus 而放弃工况与组合**：那是结构设计的核心概念，Abaqus 也在线性摄动步里保留了荷载工况。
